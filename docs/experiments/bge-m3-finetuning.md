## 2. Objective

Delveta's retrieval pipeline embeds chunks and queries with a dense model served by TEI. The
objective of this experiment was to fine-tune `BAAI/bge-m3` for the *Delveta* capability corpus,
under one contrastive objective, without introducing a second task, head, or loss.

Explicit **non**-objectives: no classifier, no "Task A / Task B" split, no sparse/ColBERT heads,
no re-opening the frozen dataset, and no claim about retrieval improvement (loss is not a
retrieval metric).

## 7. Manifest and Capability Alignment

`bge_m3_train_manifest.jsonl` is a row-aligned sidecar: row *i* describes row *i* of the data
file. The **only** field training consumes is `gold_capability_id`; `task` / `declared_lang` /
`language_profile` / `source` / `seed_family` / `negative_provenance` are recorded provenance.

`dual_target_alignment.validate(data, manifest)` recomputes alignment from bytes on disk and
fails loudly on any mismatch: equal row counts, required keys present, and
`sha256(data[i]["query"]) == manifest[i]["query_sha256"]` for every row. Startup order is
fail-fast: (1) `--train_data` must be a single JSONL **file** (a directory would be concatenated
by FlagEmbedding and break alignment); (2) alignment validate; (3) capability map; (4)
`per_device_train_batch_size <= number of distinct capabilities`.

## 8. Capability-Unique Batch Sampler

**Why.** With default in-batch negatives, any batch carrying two records of one capability turns
one record's positive text into another record's in-batch *negative* — a false negative that
corrupts the contrastive signal. The dual-target set gives both targets of a query the **same**
`gold_capability_id`, so this collision is likely by default.

`CapabilityUniqueBatchSampler` guarantees, at the `DataLoader` level, that **every batch carries
at most one record per `gold_capability_id`** — removing that class of false negative without
touching the loss.

Contract per epoch:

| Invariant | Guarantee |
|---|---|
| index coverage | every index emitted exactly once (`index_loss = 0`) |
| no duplicates | no index emitted twice (`index_dup = 0`) |
| batch uniqueness | each yielded batch has distinct capabilities |
| tail batch | a smaller trailing batch is **emitted**, never dropped |
| infeasible batch size | `batch_size > distinct capabilities` is **rejected** (never clamped) |

Mechanics: rows are built by a min-heap "smallest row first" assignment (each capability popped
at most once per row → uniqueness; balanced sizes); row count is
`max(ceil(N / batch_size), max_capability_count)`; batches are explicit index **lists** (a
`batch_sampler`), so `DataLoader` yields them verbatim. The class subclasses the fork's
`BatchRebalanceSampler`, so `Trainer._get_dataloader` routes it through `batch_sampler=` and
neutralises the accelerator shard — keeping default in-batch negatives intact. Injection is
through `CapabilityUniqueSamplerMixin._get_train_sampler`; the mixin stays left-most in the MRO
(`M3DualTargetTrainer(CapabilityUniqueSamplerMixin, EncoderOnlyEmbedderM3Trainer)`), so the
official M3 loss and checkpoint layout are untouched.

## 14. Model Variants — Generation

The fine-tuned model is published as **three parallel variants inside one Hugging Face
repository** — not three repositories, and with **no model copy at the repository root**. All
three share one embedding semantic: `normalize(last_hidden_state[:, 0])`.

| Variant | Path | Format | Generation |
|---|---|---|---|
| FP32 (master) | `FP32/` | safetensors, float32 | none — the trained `checkpoint-2027`, byte-identical to the source |
| FP16 (derived) | `FP16/` | safetensors, float16 | dtype cast of FP32 (`torch` 2.14.1, `safetensors` 0.8.0) |
| INT8 (derived, CPU) | `INT8/` | ONNX, dynamic int8 | `torch.onnx.export` (opset 17, dynamic batch/seq) then `onnxruntime.quantization.quantize_dynamic(weight_type=QInt8)` |

The INT8 export wraps encoder + **CLS pooling** + **L2 normalization** in one module, so pooling
and normalization are *inside* the graph and raw hidden states are not exposed as the embedding.
INT8 tooling: `torch` 2.14.1+cpu, `onnx` 1.23.1, `onnxruntime` 1.30.0, built in an isolated
environment (`/workspace/_onnx_env`).

> `torch.onnx.export` may emit **external-data sidecar** weight files next to the `.onnx` (it did
> for the fp32 export). Verify the exported `model.onnx` loads from a directory containing
> **only** `model.onnx`, then remove the sidecars.

## 16. Evaluation Methodology

Four measurement families are kept strictly apart and are **not** interchangeable:

| Family | Question | Status |
|---|---|---|
| A. Training metrics | did optimisation proceed sanely? | recorded (§12) |
| B. Embedding numerical consistency | do FP32 / FP16 / INT8 agree numerically? | recorded, 12-query sample (§15) |
| C. Retrieval effectiveness | is retrieval actually better? | **NOT YET COMPLETED** (§18) |
| D. Runtime performance | what does it cost to run? | recorded, this CPU (§17) |

Metric definitions (for family C, when a harness exists):

| Metric | Definition |
|---|---|
| Recall@k (k = 1, 3, 5, 10) | fraction of queries whose gold target appears in the top-*k* retrieved items |
| MRR | mean over queries of `1 / rank` of the first correct item |
| Capability retrieval recall | fraction of queries whose gold **capability** is retrieved into the candidate set |
| Capability selection recall | fraction of queries whose gold capability is *selected* downstream given the candidate set |

A valid FP32 / FP16 / INT8 comparison must hold fixed: the test queries, the candidate corpus,
query preprocessing, text encoding, retrieval/ranking logic, gold labels, and the metric
implementation; results are reported as absolute values plus the delta vs FP32.

## 17. Runtime Performance

Host: **AMD EPYC 7542**, 8 threads, batch size 12, input length 64.

| Metric | INT8 (ONNX Runtime) | FP32 (PyTorch, reference) |
|---|---:|---:|
| Model file size | 568 511 234 B (~542 MiB) | 2 271 064 456 B (~2.11 GiB) |
| Load time | 1.285 s | 0.278 s |
| Single-query latency | 32.7 ms | 95.7 ms |
| Batch latency (batch of 12) | 288.7 ms | 275.8 ms |
| Peak RSS | 1607 MB | 1910 MB |

- **The two columns are different runtimes** — INT8 under ONNX Runtime, FP32 under PyTorch — so
  the latencies are **not** an apples-to-apples quantization-vs-baseline comparison. The
  meaningful signals are the **file size** and **peak RSS**; within the ONNX Runtime column,
  latency is comparable to itself only.
- GPU peak (formal training): 11 459.1 MB allocated / 13 558.0 MB reserved on an A30 24 GB. GPU
  **inference** latency for the variants has not been measured.
- Latency measured on different devices or at different batch settings must not be used to
  conclude which quantization is "better".

## 18. Evaluation Results and Open Items

**Family B (embedding numerical consistency)** — recorded in §15. Scope caveat: a **12-query**
sample on a **single** machine; it is a consistency check between variants, not a general
embedding-quality or retrieval statement. The sample is too small to extend into a general
conclusion.

**Family C (retrieval effectiveness): NOT YET COMPLETED.**

No Recall@k, MRR, or capability-recall number is reported for the fine-tuned model, because **no
validated post-finetuning retrieval evaluation harness is in place**. Reporting numbers would
require running the full retrieval pipeline; none has been run for this model, and no number is
fabricated.

> Post-finetuning retrieval evaluation: NOT YET COMPLETED.

**INT8 retrieval effectiveness: BLOCKED.** The current evaluation harness does not support the
ONNX Runtime path, so the quantized variant cannot be scored through the same protocol as FP32 /
FP16. What is missing is a small adapter that runs the ONNX-INT8 build through the same
encode → rank → score path used for the PyTorch variants.

> Embedding cosine similarity (Family B) is **not** a retrieval-effectiveness metric and is
> **not** a substitute for Family C. Training loss decreased, but this alone does not establish
> retrieval improvement.

## 19. Reproducibility

Stages, in order:

```bash
# GPU host
python train_bge_m3_dual_target.py \
  --train_data data/bge_m3_train.jsonl --train_manifest data/bge_m3_train_manifest.jsonl \
  --model_name_or_path BAAI/bge-m3 --local_files_only \
  --output_dir /workspace/_bge_formal_out \
  --per_device_train_batch_size 8 --train_group_size 8 \
  --learning_rate 1e-5 --num_train_epochs 1 \
  --query_max_len 64 --passage_max_len 64 --bf16

# FP32 = checkpoint-2027 (no conversion); FP16 = dtype cast; INT8 = ONNX export + dynamic quant
# then upload FP32/ FP16/ INT8/ into one HF repo and verify per-file size + LFS sha256
```

What must hold for a rerun to be comparable:

1. Base revision `5617a9f61b028005a4858fdac845db406aefb181` and FlagEmbedding 1.4.2.
2. The frozen bundle unchanged — the SHA256s in §5 (train / manifest / test).
3. Dense-only (`unified_finetuning=False`) and default in-batch negatives (the training file
   carries **no** `.no_in_batch_neg` suffix).
4. Capability-unique batching and the same `train_group_size` / seq lengths / batch size.

Determinism caveat: the algorithm seeds the sampler (`seed=42`), but bit-exact reproduction
across a different GPU or torch build is **not** claimed — cuDNN/cuBLAS kernel selection is not
fixed. A rerun should reproduce the *decision* (1 epoch / 2027 steps, finite decreasing loss) and
metrics within normal run-to-run noise, not the bytes.

## 21. Known Limitations

1. **No retrieval-effectiveness number exists** (§18). The loss curve is not a retrieval metric.
2. **Embedding consistency is a 12-query single-machine sample** (§15) — too small for general
   conclusions.
3. **INT8 retrieval is BLOCKED** on an ONNX adapter in the harness (§18).
4. **Not a general-purpose drop-in** for `BAAI/bge-m3`; it targets the Delveta capability corpus.
5. **Runtime numbers span two runtimes** (PyTorch vs ONNX Runtime); only file size / peak RSS are
   comparable across columns (§17).
6. **Determinism is not bit-exact** across GPUs / torch builds (§19).
